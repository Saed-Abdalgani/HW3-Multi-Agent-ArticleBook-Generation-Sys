## 1. Overview

### 1.1 Purpose
This system uses a **CrewAI** team of cooperating AI agents to autonomously research,
write, and typeset a long-form document (an article or short book) on a user-selected
topic, and to compile it into a **professional, print-ready PDF** using a **LaTeX**
toolchain. The pipeline is designed around a Markdown-first authoring flow that is later
converted to `.tex` for final compilation, maximizing review speed while preserving
typographic quality.

### 1.2 Problem Statement
Producing a well-structured, 15–20 page document with consistent formatting, correct
bibliography linking, embedded graphics, mathematical notation, and **mixed
Hebrew–English (BiDi)** text is slow and error-prone when done manually. The challenges
compound when content, layout, and citation management must all stay synchronized through
multiple compilation passes.

### 1.3 Solution Summary
A modular agent crew, each agent owning a single responsibility (research, outline,
writing, figure generation, LaTeX assembly, compilation, and QA), coordinated by CrewAI.
Domain expertise is injected through **CrewAI Skills** (file-based `.md` instruction
packages) rather than monolithic prompts, keeping each agent focused and maintainable.
The output is a fully compiled PDF with working internal links and a linked bibliography.

### 1.4 Goals and Non-Goals
**Goals**
- Generate a coherent 15–20 page document on an arbitrary topic.
- Produce a thematic cover, table of contents, headers/footers, and chapter structure.
- Embed at least one diagram, image, Python-generated graph, table, and decorated formula.
- Demonstrate correct BiDi (RTL/LTR) handling in at least one chapter.
- Produce a linked bibliography from a `.bib` source.
- Automate the full multi-pass compilation pipeline end to end.

**Non-Goals**
- Not a real-time interactive writing assistant or WYSIWYG editor.
- Not a general-purpose translation service.
- Not responsible for fact-checking beyond cited sources (human review required).
- No web-hosted multi-tenant SaaS in this scope (local/CLI execution).

## 3. Functional Requirements

### 3.1 Agent Crew (CrewAI)
- **FR-1** The system SHALL define a CrewAI crew of specialized agents with distinct
  roles: Research, Outline/Architect, Writer, Figure/Graph Generator, LaTeX Builder,
  Compilation, and QA/Reviewer.
- **FR-2** Each agent SHALL receive domain knowledge via **CrewAI Skills** (`.md` packages
  under a `skills/` directory) and operational ability via **Tools**.
- **FR-3** Skills SHALL be attachable per-agent (`skills=[...]`), at the crew level, or
  loaded programmatically (`discover_skills` / `activate_skill`), with agent-level
  definitions overriding crew-level ones.
- **FR-4** A dedicated **LaTeX-generation agent** SHALL convert finalized Markdown content
  into valid `.tex` source files.

### 3.2 Content Generation
- **FR-5** The system SHALL accept a topic and language (Hebrew or English) as input.
- **FR-6** Content SHALL be authored first in **Markdown** for fast review, then converted
  to `.tex` only when content is complete.
- **FR-7** Generated content SHALL be **15–20 pages** in the final PDF.
- **FR-8** The document SHALL include a **table of contents**, division into
  **chapters/sections**, and **headers/footers**.

### 3.3 Required Document Elements
- **FR-9** The document SHALL contain at minimum: one **diagram**, one **image**, one
  **graph generated by Python code**, one **table**, and one **mathematical formula**.
- **FR-10** Formulas SHALL be rendered using a math package as **properly typeset
  (decorated) equations**, never as plain text.
- **FR-11** Python-generated graphics SHALL be saved to disk and referenced by correct
  relative paths in the `.tex` source.

### 3.4 Cover and Layout
- **FR-12** The system SHALL generate a **thematic cover page** containing title, author
  name, date, and language of the document.

### 3.5 BiDi (Hebrew–English) Support
- **FR-13** At least one chapter SHALL demonstrate a **correct RTL↔LTR transition**,
  with Hebrew and embedded English/technical terms rendered in correct reading order.
- **FR-14** When the target language is Hebrew, the entire layout (TOC, headers, captions,
  table/figure numbering) SHALL render correctly in RTL.

### 3.6 Bibliography and Citations
- **FR-15** Sources SHALL be stored in a **`.bib` file** and compiled with **BibTeX/biber**.
- **FR-16** The final document SHALL include a **bibliography list** at the end with
  **clickable, linked in-text citations** that jump to the corresponding entry.

### 3.7 Compilation Pipeline
- **FR-17** The system SHALL compile using **MiKTeX** with **LuaLaTeX** (preferred) or
  **XeLaTeX**.
- **FR-18** The pipeline SHALL run the engine once, then BibTeX/biber, then **2–3
  additional engine passes** until all references and citations resolve.
- **FR-19** Compilation failures SHALL surface clear diagnostics (log excerpt, failing
  pass) to the QA agent and the user.

### 3.8 Quality Assurance
- **FR-20** A QA step SHALL verify the technical contract: internal links resolve,
  citations exist and link correctly, Table/Figure entries appear in the indexes without
  breaking visual marking, and formulas are typeset (not plain text).

## 4. Non-Functional Requirements

| ID | Category | Requirement |
|----|----------|-------------|
| NFR-1 | Maintainability | Each agent and skill is single-responsibility; skills are file-based `.md` packages that can be added, replaced, or removed without code changes. |
| NFR-2 | Scalability | The crew topology supports adding chapters, agents, or skills without rewriting orchestration; figure generation parallelizable. |
| NFR-3 | Reproducibility | Given the same topic, model, and seed/config, a run produces a deterministic project structure and reproducible compilation. |
| NFR-4 | Portability | Runs locally on Windows with MiKTeX; LaTeX engine and `.bib` toolchain are standard and bundled with MiKTeX. |
| NFR-5 | Reliability | The compilation pipeline retries the required passes and fails loudly with actionable logs rather than producing a silently broken PDF. |
| NFR-6 | Performance | A full run (research → PDF) completes within a practical wall-clock budget for a 15–20 page document on a standard developer machine. |
| NFR-7 | Internationalization | Full Unicode + BiDi support via LuaLaTeX/XeLaTeX with appropriate Hebrew-capable fonts. |
| NFR-8 | Observability | Each pipeline stage logs inputs, outputs, and artifacts (Markdown, `.tex`, figures, logs) to a structured working directory. |
| NFR-9 | Security | API keys are read from environment/secret storage, never hard-coded or logged. |
| NFR-10 | Clarity | Generated source (`.tex`, `.bib`) is human-readable and well-commented to allow manual touch-ups. |

## 5. User Stories

- **US-1** As a submitter, I want to provide a topic and language and run a single command,
  so that I receive a compiled, requirement-compliant PDF.
- **US-2** As a submitter, I want to review content in Markdown before LaTeX conversion,
  so that I can catch issues quickly and cheaply.
- **US-3** As an author, I want each agent guided by a focused skill file, so that output
  quality is consistent and the system is easy to tune.
- **US-4** As an author, I want figures (diagram, image, Python graph) auto-generated and
  correctly linked, so that I don't manage asset paths manually.
- **US-5** As a Hebrew-language user, I want a chapter that correctly mixes Hebrew and
  English, so that BiDi rendering is demonstrably correct.
- **US-6** As a researcher, I want in-text citations that link to a `.bib`-driven
  bibliography, so that clicking a citation jumps to its reference.
- **US-7** As an evaluator, I want the PDF to contain all required elements (cover, TOC,
  headers/footers, diagram, image, graph, table, formula, BiDi, bibliography), so that I
  can verify compliance at a glance.
- **US-8** As a developer, I want clear compilation diagnostics, so that I can resolve
  unresolved references or broken links efficiently.
- **US-9** As a developer, I want to add a new chapter or skill without rewriting the
  orchestration, so that the system stays extensible.

## 6. Success Metrics

| Metric | Target |
|--------|--------|
| Requirement compliance | 100% of FR-9 elements present (diagram, image, Python graph, table, formula) |
| Page count | Final PDF is 15–20 pages |
| Link integrity | 100% of in-text citations and cross-references resolve to valid targets |
| Bibliography correctness | All cited entries present in `.bib`; no orphan or missing citations |
| BiDi correctness | At least one chapter with verified, correct RTL↔LTR transitions |
| Compilation success | Clean build after the prescribed pass sequence (engine → bib → 2–3 passes) |
| Formula typesetting | 100% of formulas rendered as decorated math, 0 plain-text formulas |
| Reproducibility | Re-running with the same config yields a successfully compiling project |
| Manual intervention | Zero manual edits required between run start and final PDF |

## 7. Assumptions and Dependencies

- **MiKTeX** is installed with LuaLaTeX/XeLaTeX and BibTeX/biber available on `PATH`.
- A Hebrew-capable Unicode font (e.g., a David/Frank Ruehl class font) is installed.
- **Python 3.x** with a plotting library (e.g., Matplotlib) is available for graph generation.
- **CrewAI** and required tool packages are installed; LLM API credentials are configured.
- The user supplies the topic and target language; Hebrew is encouraged and evaluated favorably.

## 8. Out of Scope / Future Enhancements

- Web UI or hosted multi-user service.
- Automated factual verification of generated claims.
- Multi-language output beyond Hebrew/English BiDi in a single document.
- Continuous regeneration / incremental rebuilds based on diffs.

## 9. Acceptance Criteria (Definition of Done)

The deliverable is accepted when a single run produces a 15–20 page PDF that contains a
thematic cover (title, author, date, language), TOC, chapters with headers/footers, at
least one each of diagram/image/Python-graph/table/decorated-formula, a chapter with
correct BiDi handling, and a linked bibliography — all internal links and citations
resolving correctly after the prescribed compilation sequence.
